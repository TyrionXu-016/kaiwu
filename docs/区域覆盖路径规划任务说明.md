### 训练流程简介

官方材料中的**完整训练流程示意图**请以开悟平台 / 开发指南为准；其逻辑可概括为下列环节：

| 环节 | 介绍 |
|------|------|
| **智能体—环境循环交互** | 将环境给出的观测与奖励处理为符合**预测函数**的输入；调用预测得到**动作**；再处理为环境可接受的指令；环境执行后**状态转移**，返回新观测与奖励。 |
| **样本处理** | 从开始到结束的交互过程为 **episode**；单次交互的结构化数据为**样本**；一条 episode 的样本序列为**轨迹**；对轨迹加工为规范化训练样本（**`SampleData`**）。 |
| **模型迭代优化** | 基于训练样本，用算法（如 PPO）**更新模型参数**，优化策略。 |
| **智能体加载新模型** | 智能体载入**最新模型**，继续与环境循环采样。 |

上述闭环由**强化学习分布式计算框架**中的**训练工作流**调度实现（单机或分布式训练 / 评估以平台与配置为准）。

### 三大核心模块

| 模块 | 作用 |
|------|------|
| **强化学习环境系统** | 标准环境接口，完成智能体与环境的交互。 |
| **强化学习智能体开发套件** | 标准智能体接口，以及**算法库**、**模型组件库**等工具函数，用于快速搭建智能体。 |
| **强化学习分布式计算框架** | 标准接口，按需实现**训练工作流**，运行单机或分布式训练、评估（**KaiwuDRL** 详见 **「分布式计算框架」**）。 |

## 环境：强化学习环境系统与标准接口

综述中已说明：训练流程依赖智能体与环境的持续交互。本节概括**强化学习环境系统**在开悟框架中的角色及**标准接口**；具体观测 / 状态字段仍以**所使用环境的数据协议**为准（本文 **§18**）。

### 概述

- **强化学习环境**：给定**动作**输入，产生**观测**、**奖励**等反馈，用于刻画 RL 所求解的**问题场景**。
- **场景适配**：框架通过场景适配模块**封装仿真器**，将其特化接口 / 协议转换为**统一的环境接口与协议**，供智能体调用。

### 环境系统主要能力

1. **接收配置**：初始化时读入配置，决定元素初始状态等（如本题 `usr_conf` / `train_env_conf.toml`，见 §10）。  
2. **输出观测与奖励**：供智能体 **预测、训练**。  
3. **输出其它信息**：如可视化、日志等，供监控、调试等组件使用。  
4. **接收动作**：执行一次**状态转移**，产生下一步观测与奖励。

### 环境使用方式

- 不同场景的观测、奖励**数据结构不同**，须查阅该环境的**官方数据协议**（本题见 **§18**）。  
- 在训练工作流 **`workflow`** 中取得**环境实例**后，通过下列**标准函数**完成交互。

### `reset(usr_conf)`

将环境恢复为配置所描述的状态，并返回**初始观测**及**全局状态**。

```python
# usr_conf：由环境配置文件解析得到的 dict，传入 reset
obs, state = env.reset(usr_conf=usr_conf)
```

| 参数 / 返回 | 类型 | 说明 |
|-------------|------|------|
| **`usr_conf`** | `dict` | 环境配置（如 TOML 解析结果） |
| **返回值 `obs`** | `dict` | 初始**环境观测** |
| **返回值 `state`** | `dict` | 初始**环境全局状态** |

### `step(act, stop_game=False)`

执行一步动作，完成状态转移，返回当前帧号、新观测、得分信号、终止标志等。

```python
frame_no, _obs, score, terminated, truncated, _state = env.step(act, stop_game=False)
```

| 参数 | 类型 | 说明 |
|------|------|------|
| **`act`** | `dict` | 本步环境可识别的**动作**载荷 |
| **`stop_game`** | `bool` | 是否**主动结束**当前对局（默认 `False`） |

| 返回 | 类型 | 说明 |
|------|------|------|
| **`frame_no`** | `int` | 当前环境实例**帧号** |
| **`_obs`** | `dict` | 当前帧**观测** |
| **`score`** | `int` | 当前帧与**得分/回报相关**的标量（官方文档表头为「奖励信息」；在本赛题语境下多与**清扫得分**一致，与 RL 塑形奖励的区别见 **§8.1**） |
| **`terminated`** | `bool` | 对局是否**结束**（如失败条件触发等，以环境实现为准） |
| **`truncated`** | `bool` | 是否**异常或截断**（如达到步数上限等，以环境实现为准） |
| **`_state`** | `dict` | 当前帧**完整状态** |

### 与本文 §11、代码包的关系

- 开悟文档中的 **`reset` → `obs, state`**、**`step` → 多返回值拆包** 描述的是**标准形态**。  
- 赛题「环境详述」或代码包中可能对返回值再做**聚合**（例如 `env_reward, env_obs = env.step(...)`，奖励在 `env_reward` 内、`env_obs` 内含 `observation` / `extra_info` 等）。**以你仓库中实际 `env` 类型与工作流调用为准**，并与 **§11、§18** 交叉核对。

## 数据处理与特征管线（智能体侧）

环境返回的**原始观测 / 状态**通常不能直接进入网络的 `predict` / `learn`。开发者需完成 **特征处理**、**样本处理**与 **RL 奖励设计**（Reward），使类型与字段符合**智能体开发套件**约定。

题述在「特征处理」小节中写「四个关键工作」，若仅列举**定义数据结构、观测处理、动作处理」三项，可理解为：其余逻辑由下文 **奖励设计**、**样本处理** 两节覆盖，共同构成完整数据处理链路。

### 定义数据结构

**开发位置**：`<智能体目录>/feature/definition.py`（标准包下多为 `agent/feature/definition.py`）。

使用框架提供的 **`create_cls`** 动态定义训练流程依赖的三类结构（**属性名与数量可自定**）：

| 类型 | 用途 |
|------|------|
| **`ObsData`** | **`agent.predict()`** 的输入：特征、合法动作掩码等 |
| **`ActData`** | **`agent.predict()`** 的输出：离散动作、概率等 |
| **`SampleData`** | **`agent.learn()`** 使用的**训练样本**（含 `npdata` 等） |

**`create_cls` 用法**

| 参数 | 说明 |
|------|------|
| 第一个参数 | `str`，类名 |
| 其余关键字 | 类属性，默认 `None`，由开发者扩展 |

```python
ObsData = create_cls("ObsData",
    feature=None,
)
ActData = create_cls("ActData",
    action=None,
    prob=None,
)
SampleData = create_cls("SampleData",
    npdata=None,
)
```

实际项目中常在 `ObsData` 上增加 `legal_action` / `legal_act` 等字段，需与 `observation_process` 返回值一致。

### 观测处理

**开发位置**：`<智能体目录>/agent.py`。

将 `env.reset` / `env.step` 得到的**原始观测**转为 **`ObsData`**，供 `predict` 使用。复杂特征建议放在 **`feature/preprocessor.py`**，由 `observation_process` 调用（本题基线见 **§15.1～§15.2**）。

```python
def observation_process(self, obs, state=None):
    return ObsData(feature=feature, legal_act=legal_actions)
```

| 参数 | 类型 | 说明 |
|------|------|------|
| **`obs`** | `Observation`（或环境等价类型） | 环境观测 |
| **`state`** | `EnvInfo` 等（可选） | 环境状态 / 全局信息 |

| 返回 | 说明 |
|------|------|
| **`ObsData`** | 作为 **`agent.predict()`** 的输入 |

### 动作处理

**开发位置**：`<智能体目录>/agent.py`。

将 **`ActData`** 转为 **`env.step(act, ...)`** 可识别的 **`act`**（符合环境动作协议，本题见 **§12、§18.8**）。

```python
def action_process(self, act_data):
    return act_data.act
```

| 参数 | 说明 |
|------|------|
| **`act_data`** | `ActData` 实例 |

| 返回 | 说明 |
|------|------|
| 环境可解析的动作对象 | 作为 **`env.step()`** 的第一个参数 |

### 奖励设计（Reward）

**开发位置**：`<智能体目录>/feature/definition.py`（或与工作流约定的一致路径）。

- 此处 **Reward** 指 **RL 训练用奖励**，与环境中用于评价的 **Score** 不同（见 **§8.1**）。  
- 可基于观测、状态及先验知识自由塑形。

**`reward_shaping`（框架约定接口）** — 在工作流中调用：

```python
def reward_shaping(obs, _obs, state, _state):
    return reward
```

| 参数 | 说明 |
|------|------|
| 形参可扩展 | 不限个数与类型：前后观测、状态、自定义量等 |

| 返回 | 说明 |
|------|------|
| 数值 | 本步 **RL reward** |

### 样本处理

**开发位置**：`<智能体目录>/feature/definition.py`。

## 模型开发（智能体侧）

**开发位置**：`<智能体目录>/model/model.py`（标准包为 **`agent/model/model.py`**）。

```python
import torch.nn as nn
```

## 算法开发（智能体侧）

在完成**特征处理**与 **Reward 设计**（见「数据处理与特征管线」）、并在 **`model.py`** 中定义好 **网络（见「模型开发」）** 之后，需在 **`<智能体目录>/algorithm/algorithm.py`**（标准包为 `agent/algorithm/algorithm.py`）中实现**强化学习算法**：给定一批训练样本，通过约定的**优化步骤**更新模型参数。更细的调度、分布式行为以**腾讯开悟分布式计算框架**文档为准。

### `learn`

**作用**：算法模块的**核心入口**——消费 **`list_sample_data`**，完成**损失计算、反向传播、优化器步进**（具体形式随算法而异，如 PPO 的策略 / 价值 / 熵项组合）。

```python
def learn(self, list_sample_data):
    """
    Implementing the core method of the algorithm
    实现算法的核心方法
    """
    loss = 0                         # 按所选算法计算总损失 Calculate loss
    loss.backward()                  # 反传梯度 Calculate gradient
    self.optimizer.step()            # 更新参数 Update weights
```

| 参数 | 类型 | 说明 |
|------|------|------|
| **`list_sample_data`** | `list` | 元素为 **`SampleData`** 的训练样本列表（与 `sample_process` 输出及工作流组 batch 方式衔接） |

题述伪代码中的 **`loss = 0`** 仅作占位；实际实现中应替换为 **PPO、DIY** 等对应的总损失张量（本题基线中的损失形式见 **§15.8** 及 **`algorithm.py`** 实现）。

| **`agents`** | `list` | 智能体列表；由框架按开发者在 **`<智能体>/agent.py`** 中的 **`Agent`** 类实例化后传入 |

### 训练循环示例（示意）

下列代码**仅说明关键步骤**，`run_episodes`、`Frame`、`reward_shaping`、`sample_process` 等须按项目实际拆分实现；**单机**下可直接 **`learn`**；**分布式**下 **Aisrv / Learner / MemoryPool** 等与 **`agent.learn`** 的协同见 **「分布式计算框架」**。

```python
import time

@attached
def workflow(envs, agents, logger=None, monitor=None):
    env, agent = envs[0], agents[0]
    epoch_num = 1000
    episode_num_every_epoch = 1000
    last_save_model_time = time.time()

    for epoch in range(epoch_num):
        for g_data in run_episodes(episode_num_every_epoch, env, agent, logger, monitor):
            agent.learn(g_data)
            g_data.clear()

        now = time.time()
        if now - last_save_model_time >= 300:
            agent.save_model()
            last_save_model_time = now


def run_episodes(n_episode, env, agent, logger, monitor):
    # usr_conf：由训练侧配置注入
    usr_conf = ...  # 实际从 toml / 平台配置读取

    for episode in range(n_episode):
        done = False
        collector = []

        obs, state = env.reset(usr_conf=usr_conf)
        # 首帧须先构造 ObsData，再进入 while
        obs_data = agent.observation_process(obs, state)

        agent.load_model(id="latest")  # 单机可省略远程加载逻辑

        while not done:
            act_data = agent.predict(list_obs_data=[obs_data])[0]
            act = agent.action_process(act_data)

            frame_no, _obs, score, terminated, truncated, _state = env.step(act)
            if _obs is None:
                break

            _obs_data = agent.observation_process(_obs, _state)

            if truncated and frame_no is None:
                break

            reward = reward_shaping(obs_data, _obs_data, state, _state)
            done = terminated or truncated

            frame = Frame(
                obs=obs_data.feature,
                _obs=_obs_data.feature,
                act=act,
                rew=reward,
                done=done,
            )
            collector.append(frame)

            if done:
                if len(collector) > 0:
                    # 一般为 agent.sample_process 或 feature 模块已绑定的方法
                    collector = agent.sample_process(collector)
                    yield collector
                break

            obs_data = _obs_data
            obs = _obs
            state = _state
```

- **模型保存间隔**：示例为 **300s**；平台另有保存策略限制（**§15.10**）。  
- 本题仓库中的**真实循环**以 **`train_workflow.py`** 为准，勿与上表逐行等同。

## 分布式计算框架（KaiwuDRL）

在大规模训练场景中，**分布式计算框架**是基础设施。腾讯开悟采用自研 **KaiwuDRL**（题述由王者荣耀团队研发），通过并行计算、资源调度与多角色协同，提升训练效率与稳定性。架构总览图在官方材料中常以 **`1_整体架构_图`** 等文件名提供，请以平台文档为准。

### 总体架构与组件

KaiwuDRL 包含 **Environment、Aisrv、Actor、Learner** 等 RL 组件（均可多实例），并集成通信、日志、监控、对象存储等基础能力。

| 组件 | 功能 |
|------|------|
| **Environment** | 环境服务：运行仿真环境，标准接口交互，返回观测等 |
| **Aisrv** | 训练流程**中枢**：收集环境样本、运行训练 / 评估工作流、组件间数据转发 |
| **Actor** | **预测**服务：响应 Aisrv 请求，调用智能体 **`predict()`** 或 **`exploit()`** 产出动作 |
| **Learner** | **训练**服务：从样本池按批取样本，调用智能体 **`learn()`** 做梯度与参数更新 |
| **MemoryPool** | **样本池**：存训练样本；Aisrv 写入，Learner 读取（**仅分布式训练启用**） |
| **ModelPool** | **模型池**：存模型参数；Learner 推送，Actor 拉取最新（**仅分布式训练启用**） |
| **日志** | 各组件运行日志，标准接口上报 |
| **监控** | 资源与训练指标等（与 **§15.9** 呼应） |

### 预测服务（数据流概要）

1. **Aisrv → Environment**：下发环境配置，开新 **episode**。  
2. **Environment → Aisrv**：返回原始观测。  
3. **Aisrv → Actor**：携带观测发**预测请求**。  
4. **Actor**：特征处理 + **`predict`**（或等价路径）→ 动作 → 回 **Aisrv**。  
5. **Aisrv → Environment**：执行 **`step`**，得到下一观测，循环。

### 训练服务（数据流概要）

1. **Aisrv**：预测服务持续产生轨迹；完成样本处理后将样本送入 **MemoryPool**。  
2. **Learner**：按配置 **`train_batch_size`** 等从样本池取批数据，调用 **`learn()`**；按 **`dump_model_freq`** 等落盘并同步至 **ModelPool**。  
3. **Actor**：按 **`model_file_sync_per_minutes`** 等从模型池拉**最新参数**，保证推理与训练侧一致。

### 工作流（框架视角）

| 类型 | 说明 |
|------|------|
| **训练工作流** | 开发者在 **`<智能体>/workflow/train_workflow.py`** 中实现 **`@attached def workflow(...)`**，按需编排上列服务；代码骨架见本文 **「工作流开发」**。 |
| **评估工作流** | 使用**腾讯开悟平台**项目时，评估流由**官方实现**，**不可修改**；会调用开发者实现的 **`agent.exploit(observation)`**（原始观测 **`dict`** 入参），见 **「智能体开发」**。 |

### 智能体接口（与分布式协同）

接口语义与 **「智能体开发」** 一致；分布式文档中 **`learn`** 常带 **`@learn_wrapper`**，由框架与 **Learner / 样本池**衔接。**`learn(list_sample_data)`** 中一批样本对应 Learner 按 **`train_batch_size`** 从池内采样结果。

**单机 vs 分布式（`learn`）** 与「智能体开发」中表格相同：单机在工作流中显式调用；分布式下既可能由框架循环触发训练，也可能需显式调用以**向样本池提交**等（以当前 KaiwuDRL 版本文档为准）。

**`predict` / `exploit` / `load_model` / `save_model`**：装饰器名 **`@predict_wrapper` / `@exploit_wrapper` / `@load_model_wrapper` / `@save_model_wrapper`**；参数与实现细节见 **「智能体开发」**（题述分布式材料中 **`predict`** 的 **`list_state`** 是否必选以代码包为准）。

### `conf/configure_app.toml` 中与分布式相关的 `[app]` 项

配置路径一般为项目根目录 **`conf/configure_app.toml`**（与 **`agent/conf/train_env_conf.toml`** 区分）。下列为题述摘录，**键值以平台下发模板为准**：

```toml
[app]
# 执行 learn 的时间间隔，用于调节 Learner 节奏与样本产销比
learner_train_sleep_seconds = 0.001

# 样本池（Replay buffer）容量
replay_buffer_capacity = 4096

# 样本量达容量的该比例时触发训练
preload_ratio = 1.0

# 新样本入池时淘汰旧样本的策略：Lifo / Fifo
reverb_remover = "reverb.selectors.Fifo"

# Learner 从池中采样策略：Fifo / Uniform
reverb_sampler = "reverb.selectors.Uniform"

# Learner 单批 train_batch_size
train_batch_size = 2048

# 每隔多少步 dump 模型参数文件
dump_model_freq = 1000

# Learner 推送到模型池、Actor 从模型池拉取的周期（分钟）
model_file_sync_per_minutes = 1

# Learner 每次推送与 Actor 单次拉取数量上限（题述上限 50）
modelpool_max_save_model_count = 1
```

题述说明：**Learner** 每次 **`learn()`** 使用池中一批样本；按 **`dump_model_freq`** 输出模型文件；**`model_file_sync_per_minutes`** 控制模型文件与 **ModelPool / Actor** 的同步节奏。

### 预训练模型（继续训练）

在**已有模型结构一致**前提下，可从 checkpoint 继续训练。

- **平台**：创建训练任务时在界面选择预训练模型。  
- **客户端**：将 **`.pkl`** 放入代码包约定目录（如 **`ckpt/`**），并在 **`conf/configure_app.toml`** 中配置：

```toml
# 是否启用预训练加载
preload_model = false
# 预训练权重目录相对路径；{agent_name} 指代码包内 agent_算法名 目录
preload_model_dir = "{agent_name}/ckpt"
# 与文件名中步数等标识一致，勿改原始文件名
preload_model_id = 1000
```

**示例**：加载步数 **40052** 的模型文件 **`model.ckpt-40052.pkl`** — 解压后将文件放入如 **`agent_dqn/ckpt/`**，并设置：

```toml
preload_model = true
preload_model_dir = "agent_dqn/ckpt"
preload_model_id = 40052
```

配置生效后，**Aisrv** 与 **Learner** 将按框架逻辑加载该权重继续训练。


智能体侧通过 **`@load_opponent_agent_wrapper`** 声明 **`load_opponent_agent(self, id="1")`**；题述说明**函数体可由框架提供**（`pass`），用于 PVP 等场景下固定水平对手。

### On-Policy 与 Off-Policy

| 特性 | **On-Policy** | **Off-Policy** |
|------|----------------|----------------|
| 数据来源 | 须用**当前策略**实时交互得到的新数据 | 可用历史经验（含旧策略数据） |
| 数据使用 | 多为**一次性**，更新后丢弃，保证与当前策略一致 | 可**重复采样**自回放缓冲 |
| 主要优势 | 稳定、理论性质清晰 | 样本效率高，适合交互昂贵场景 |

在 **`conf/configure_app.toml`** 中题述配置示例：

```toml
# on-policy 或 off-policy
algorithm_on_policy_or_off_policy = "on-policy"

# 输出模型参数文件的步数间隔；题述建议 on-policy 取 1，off-policy 可取 1000 降低保存频率
dump_model_freq = 1
```

具体推荐与 **`dump_model_freq`** 默认值以赛方最新模板为准。

## 1. 任务目标

在**规定最大步数**内、在**电量耗尽前**，控制**小悟机器人**清扫尽可能多的**道路污渍地面**。

- 满电电量由 `battery_max` 配置（默认 **200**）。
- **每执行一步消耗 1 格电量**；若目标不可通行或斜向移动防穿角条件不满足，智能体**停留原地**，**仍计 1 步并仍消耗 1 格电量**（见「执行逻辑」）。
- 机器人**经过**污渍道路格即完成该格清扫（无需额外动作）。
- 地图中有**充电桩**：进入充电桩**有效范围**后**立即充满**至配置的满电电量。
- 地图中有**官方机器人**：小悟需**避免进入其碰撞判定区域**；一旦发生题述的「碰撞」，**任务立即失败终止**。

---

## 2. 地图与环境

| 项目 | 说明 |
|------|------|
| 栅格尺寸 | **128 × 128** |
| 坐标系 | 左上角为原点 **(0, 0)**；**x 轴向右为正**；**z 轴向下为正**（题述为 z，实现中可能与 y 对应，以环境为准） |
| 地图数量 | 共 **15** 张：**10** 张开放训练/评估，**5** 张隐藏用于最终测评 |
| 连通性 | 道路网格**全局连通**，无孤立可行走区域 |

---

## 3. 地图元素一览

| 元素 | 说明 |
|------|------|
| **小悟机器人** | 智能体控制，唯一，在道路上移动；清扫污渍、充电、避官方机 |
| **官方机器人** | 开局按配置数量生成；在各自活动区内随机移动；路过污渍会清扫（**不计入玩家得分**，且该格再被小悟清扫**无效**） |
| **小悟出生点** | 开局随机在**非充电桩、非障碍物**的道路上；与**所有官方机器人出生点**保持距离 **≥ 5**（题述） |
| **官方出生点** | 在道路上，**均匀分布**；每个官方机的 **21×21** 活动范围**互不重叠**（题述） |
| **污渍地面** | 任务开始时**道路上均为污渍**；小悟或官方**路过**后变为已清扫 |
| **充电桩** | 数量可配置（见环境配置）；每个占 **3×3** 格；进入**充电桩范围**即充满电 |
| **道路** | 可通行区域；不可移动时**停留原地**（仍耗步、耗电，见环境详述） |
| **障碍物** | 墙、家具、户外等不可通行格 |

## 4. 小悟机器人（智能体）

| 属性 | 说明 |
|------|------|
| 数量 | **1** |
| 动作空间 | **8** 个移动方向，动作值 **0–7** |
| 视野（FOV） | 以自身为中心，上/下/左/右各扩 **10 格** → **21×21**；**充电桩提供全局绝对位置信息**（环境详述） |
| 移动速度 | **1 格 / 步**（可移动时） |
| 满电电量 | 由 `battery_max` 配置，默认 **200** |

---

## 5. 官方机器人

| 项目 | 说明 |
|------|------|
| 数量 | 由 `robot_count` 配置，范围 **1～4**（默认 **4**） |
| 活动区域 | 以出生点为中心，向**上、下、左、右各拓宽 10 格** → **21 × 21** 正方形内**随机移动** |
| 清扫 | 移动到污渍上则清扫该格；**不计分**且小悟后续清扫该格**不得分** |
| 与小悟关系 | 小悟须**避免碰撞**（见下节） |

---

## 6. 碰撞与失败判定（小悟 vs 官方）

题述两种等价表述可合并理解：

- **距离判定**：小悟与官方机**距离 ≤ 1 格**即视为碰到；或理解为小悟进入**以官方机器人为中心的 3×3 邻域**。
- **后果**：**任务立即终止**，状态为 **failed**。

策略上应按 **3×3 危险区** 或 **距离 ≤ 1** 建模，并与环境 SDK 的精确判定对齐。

---

## 7. 充电桩

- 每个充电桩占地 **3×3**。
- 小悟进入充电桩**范围内**后，**立即**将电量恢复至**满电**（`battery_max`）。

---

## 8. 计分规则

| 项目 | 说明 |
|------|------|
| 任务得分 | **清扫得分** = 小悟清扫的**污渍道路格数** |
| 计分方式 | 每清扫 **1** 格污渍，得分 **+1** |
| 不计分 | 官方机器人清扫的格子；**已被官方清扫**的格子，小悟再经过**不得分** |

### 8.1 得分 vs 强化学习中的 reward

- 接口返回的 **`env_reward` 中的 `reward`（float）** 表示当前状态下的**任务得分相关**反馈，用于衡量模型表现与评价指标。
- 须与强化学习里经设计的 **`reward`（奖励函数）** 区分：后者通常由用户在智能体/工作流中定义或塑形。

---

## 9. 终止条件与任务状态

### 9.1 任务状态协议（`running` / `completed` / `failed`）

| 状态值 | 说明 |
|--------|------|
| **`running`** | 任务进行中 |
| **`completed`** | 任务**正常完成**（达到**最大步数**） |
| **`failed`** | 任务**失败**（**电量耗尽**或**碰撞官方机器人**）；具体原因见协议中的 **`fail_reason`** 等字段（以 SDK 为准） |

### 9.2 终止原因与状态对照

| 终止原因 | 协议侧理解 | 说明 |
|----------|------------|------|
| 达到最大步数 | **`completed`** | 正常结束本局 |
| 电量耗尽 | **`failed`** | `battery ≤ 0` |
| 与官方机器人碰撞 | **`failed`** | 进入官方碰撞判定即失败 |

**`env_obs` 布尔字段**（见 §11.4）：**`terminated`** 多对应「非 running 的结束」；**`truncated`** 常对应「步数截断或异常」等，**以实际 SDK 与数据协议为准**。

## 12. 动作空间与执行逻辑

动作值与 `(dx, dy)` 的**官方枚举**与 **§18.8、§18.9** 一致。

### 12.1 动作值与方向（向量 `(dx, dy)`）

题述 **dy**：**向上为负、向下为正**（与常见屏幕坐标一致）。

| 动作值 | 方向 | 向量 `(dx, dy)` | 说明 |
|--------|------|-----------------|------|
| 0 | 右 → | `(1, 0)` | 向右移动 1 格 |
| 1 | 右上 ↗ | `(1, -1)` | 向右上移动 1 格 |
| 2 | 上 ↑ | `(0, -1)` | 向上移动 1 格 |
| 3 | 左上 ↖ | `(-1, -1)` | 向左上移动 1 格 |
| 4 | 左 ← | `(-1, 0)` | 向左移动 1 格 |
| 5 | 左下 ↙ | `(-1, 1)` | 向左下移动 1 格 |
| 6 | 下 ↓ | `(0, 1)` | 向下移动 1 格 |
| 7 | 右下 ↘ | `(1, 1)` | 向右下移动 1 格 |

方向图示：

```text
        上(2)
    左上(3) | 右上(1)
       \   |   /
  左(4)----+----右(0)
       /   |   \
    左下(5) | 右下(7)
        下(6)
```

### 12.2 合法动作

- **`legal_act`**：长度为 8 的整数数组；题述为**全 1**，表示 8 个方向均可**尝试**移动（实际是否位移由地形与斜向规则决定）。

### 12.3 移动规则（执行逻辑）

1. **直线移动**：目标格子**可通行**即可移动到该格。
2. **斜向移动（防穿角）**：目标格子可通行，且**水平与垂直相邻两格中，至少有一侧边的相邻格可通行**，避免沿墙角「穿角」；不满足则不可移动到目标格。
3. **碰撞处理**：若目标不可通行，或斜向条件不满足，智能体**停留原地**，但仍消耗 **1 步**和 **1 格电量**。

## 14. 策略设计备忘（非官方）

- **覆盖 + 续航**：在电量与 `max_step` 约束下规划回路，结合充电桩全局位置做补能。
- **禁区动态更新**：每步根据官方机位置更新 **3×3（或距离 ≤1）** 危险区；必要时绕开官方 **21×21** 区域边缘。
- **无效动作成本**：`legal_act` 全 1 时仍可能原地不动且扣电，需避免在障碍侧反复「撞墙」浪费步数与电量。
- **地图语义**：`map_info` 格值见 **§18.10**；结合 `frame_state` / `env_info` 可区分官方已清与小悟可得分区域（以数据协议字段为准）。

## 15. 智能体详述（代码包基线）

代码包内提供的是**最简基线**：具备基础清扫相关逻辑，**不包含**充电桩导航、官方机器人（NPC）躲避等进阶能力。选手需结合环境与数据协议，自行扩展**特征工程、奖励设计、模型结构**等。

### 15.1 观测处理

`observation_process` / `ObsData` 的**通用约定**见上文 **「数据处理与特征管线」**；以下为**本题基线**写法。环境返回的 **`observation`** 为针对智能体的**局部观测**（及关联信息），可在 **`observation_process`** 中处理。推荐使用预处理器 **`preprocessor`** 对 `env_obs` 做预处理，例如：

```python
def observation_process(self, env_obs):
    feature, legal_action, reward = self.preprocessor.feature_process(env_obs, self.last_action)
    obs_data = ObsData(
        feature=list(feature),
        legal_action=legal_action,
    )
    remain_info = {"reward": reward}
    return obs_data, remain_info
```

### 15.2 特征处理（基线 69 维）

| 部分 | 维度 | 含义 |
|------|------|------|
| `local_view` | **49** | 以小悟为中心的 **7×7** 局部地图（`0` 障碍，`1` 已清扫，`2` 污渍），归一化到 **[0, 1]** |
| `global_state` | **12** | 全局状态：步数归一化、电量比、清扫进度、剩余污渍比、坐标归一化、**4 方向污渍距离**、最近污渍距离、是否接近污渍等 |
| `legal_action` | **8** | 移动方向**合法掩码**（对应动作 **0～7**） |
| **合计** | **69** | — |

说明：环境原始 **`map_info` 为 21×21**（见 §11.5）；基线将其中 **7×7** 抽成 `local_view`，属于**工程上的简化**，扩展时可改用更大感受野或 CNN 等。

### 15.3 奖励处理（基线）

| 奖励项 | 含义 | 数值 |
|--------|------|------|
| `cleaning_reward` | 每步清扫格子数奖励 | **+0.1 ×** 本步清扫格数 |
| `step_penalty` | 每步时间惩罚（鼓励效率） | **-0.001** |

**每步 RL 奖励**：`reward = cleaning_reward + step_penalty`。

**时序**：使用 **GAE**（`Config.GAMMA`、`Config.LAMDA`）计算 **advantage** 与 **reward_sum**，作为 **PPO** 的训练目标。

### 15.4 算法概览

算法模块入口 **`learn(list_sample_data)`** 的接口约定见上文 **「算法开发」**。

| 算法 | 说明 |
|------|------|
| **PPO** | Proximal Policy Optimization，稳定性较高、收敛较快 |
| **DIY** | 自定义算法模板目录，可自行实现其他算法 |

### 15.5 模型设计（基线 Actor-Critic）

`Model` 类的**接口与继承关系**见上文 **「模型开发」**。单 **MLP 骨干** + **双头**：

```text
输入 (69D) → MLP 骨干 (69 → 128 → 64) → Actor 头 (64 → 8)  → 动作 logits
                                      → Critic 头 (64 → 1) → 状态价值
```

选手可自行替换为更复杂结构（CNN、注意力等，见 §17）。

### 15.6 动作输出

训练 / 评估时 **`predict` / `exploit` 的对外接口**见 **「智能体开发」**。

- 动作空间：**8** 维离散（移动方向 **0～7**）。
- **合法动作掩码 `legal_action`**：对非法方向在 logits 上施加**大负数**后再 **softmax**，等价于从分布中排除非法动作。
- **采样**：训练时对分布 **multinomial** 随机采样；评估时通常 **argmax** 取概率最大动作。

### 15.7 训练流程（概要）

编排层面的 **`workflow`** 与循环骨架见 **「工作流开发」**。

1. **交互采样**：Agent 与环境交互生成 **`SampleData`**（含 `obs`、`action`、`prob`、`value`、`reward` 等）。
2. **后处理**：填充 **`next_value`**，用 **GAE** 计算 **advantage**、**reward_sum**。
3. **更新**：在批次数据上做 **PPO** 更新（策略损失、价值损失、熵正则）。
4. **保存 / 评估**：周期性保存模型，在验证地图上评估。

### 15.8 损失函数（基线形式）

```text
total_loss = vf_coef × value_loss + policy_loss - beta × entropy_loss
```

- **`value_loss`**：Clipped 价值损失  
- **`policy_loss`**：PPO Clipped surrogate 目标  
- **`entropy_loss`**：策略熵正则（鼓励探索）

### 15.9 算法监控信息

平台 / 客户端可查看算法上报指标；**面板操作、`MonitorConfigBuilder`、`push_data`、基础/硬件指标表**见 **「监控与日志」**。基线常见项：

| 指标名称 | 说明 |
|----------|------|
| `total_loss` | 总损失 |
| `policy_loss` | 策略损失 |
| `value_loss` | 价值损失 |
| `entropy_loss` | 熵损失 |
| `reward` | **累计回报**（RL 训练用回报，与任务清扫得分概念不同，见 §8.1） |

可在 **`agent_{算法名}/conf/monitor_builder.py`**（如本题 **`agent_ppo/conf/monitor_builder.py`**）中自行增加监控指标。

### 15.10 模型保存（平台限制）

开悟平台对保存频率有**安全限制**（随任务类型而异）。基线默认约 **每 30 分钟**保存一次模型；可自行改写保存逻辑，但需符合平台规则。
